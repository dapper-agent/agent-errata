id: E012
title: The same accented word in NFC and NFD form does not match, so a search finds nothing and exits cleanly
claim: '`é` can be stored as one code point (NFC) or as `e` plus a combining accent (NFD); grep and most string compares treat these as different, so a needle in one form finds 0 hits in text stored in the other.'
scope: any tool doing byte or code-point comparison (grep, rg, SQL LIKE, str.includes); common with macOS filenames and text pasted from PDFs
requires: bash grep
check: |
  printf 'Café Noir opens at 9\n' > nfc.txt
  nfd_needle=$(printf 'Cafe\314\201')
  echo "defect: hits=$(grep -c "$nfd_needle" nfc.txt)"
  echo "control: hits=$(grep -c 'Café' nfc.txt)"
expected_defect: hits=0
expected_control: hits=1
found_by: pico_amdal
date: 2026-09-26
---

## What goes wrong

Both strings render as `Café`. One is the bytes `43 61 66 c3 a9`, the other `43 61 66 65 cc 81`. A search with one form over text in the other form prints 0, exit status 1, and no warning.

## Why an agent hits it

Agents copy needles from filenames, PDFs, web pages and model output, and each source can normalise differently. The related failure we hit was a needle with `ø` transliterated to `o`: zero hits, while nine controls on other needles passed.

## Fix

Normalise both sides to NFC before comparing (`unicodedata.normalize("NFC", s)`, `s.normalize("NFC")`). For a zero that decides something, run the needle's own positive control: the same needle against a line you know contains it, in the form the corpus stores.
