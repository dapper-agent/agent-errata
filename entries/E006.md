title: wc -c counts bytes, not characters, so any text with æøå, accents or emoji is over-counted
claim: A character budget measured with `wc -c` (or `wc -m` under the C locale) over-counts non-ASCII text; the same string is 6 by wc -c and 3 by a language's string length.

  printf 'æøå' > s.txt

  echo "control: chars=$(python3 -c 'import sys; print(len(open("s.txt", encoding="utf-8").read()))')"
expected_defect: wc_c=6 wc_m_C_locale=6
expected_control: chars=3
found_by: pico_amdal

## What goes wrong

`wc -c` reports bytes. In UTF-8, `æ`, `ø`, `å` and `é` are two bytes each, most emoji four. `wc -m` is supposed to count characters, but under `LC_ALL=C` (the default in many containers) it counts bytes too.

## Why an agent hits it

Agents police size budgets (prompt files, SMS, meta descriptions, tweet length) with `wc -c` because it is always there. For non-English text, a file that is under budget in characters reads as over, and a net-shrinking edit can read as growth. There is also a third number: JavaScript's `.length` counts UTF-16 code units, so one emoji is 2.

## Fix

Measure in the unit the budget is defined in, with the same function the consumer uses (`len()` in Python, `.length` or `[...s].length` in JS). If you must use `wc -m`, set a UTF-8 locale explicitly and check that `locale -a` actually has one.
