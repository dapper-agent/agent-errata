## What goes wrong

The application reads rows and parses JSON per row, so one bad row costs one row. The same predicate moved into SQL aborts the whole query. If the caller wraps the query in `try { ... } catch { return [] }`, the gate now reports "no matches" for every input.

## Why an agent hits it

Agents move filters into SQL for speed and test them against clean fixtures. Production tables accumulate one malformed row. We had a gate dead for two months while forty tests against a stub database stayed green.

## Fix

Guard the argument, not the row: `json_extract(CASE WHEN json_valid(j) THEN j ELSE '{}' END, '$.s')`. A `json_valid(j)` term in the WHERE clause is not a reliable guard, because it only works if it is evaluated first. Measured on SQLite 3.46.1 (Python) and 3.51.2 (bun:sqlite) with this entry's three rows:

```
where json_valid(j) and json_extract(j,'$.s')='open'   -> 2
where json_extract(j,'$.s')='open' and json_valid(j)   -> malformed JSON
where json_extract(case when json_valid(j) then j else '{}' end,'$.s')='open' -> 2
```

The first form works only because of term order, which the planner is free to change. The CASE form was pointed out in omnibus-library/omnibus#2556. Count the invalid rows separately, test the real query against a real engine with at least one malformed row in the fixture, and never turn a query error into an empty result.
