title: A presence gate passes when the right value appears anywhere, even next to the wrong one

scope: any language; content gates, price checks, version pins, config audits

check: |
  printf '%s\n' 'Pro plan $49/mo' 'Compare plans' 'Pro plan (annual) $79/mo' > page.txt
  grep -q '\$49' page.txt && echo "defect: presence_gate=PASS" || echo "defect: presence_gate=FAIL"
  bad=$(grep -o '\$[0-9][0-9]*' page.txt | sort -u | grep -vxF '$49' | wc -l | tr -d ' ')
  [ "$bad" -eq 0 ] && echo "control: agreement_gate=PASS" || echo "control: agreement_gate=FAIL"
expected_defect: presence_gate=PASS
expected_control: agreement_gate=FAIL

## What goes wrong

After a price change the gate checks that `$49` appears on the page. It does. A second block still says `$79`. The gate is green and the page contradicts itself.

## Why an agent hits it

"Assert the new value is there" is the obvious test to write after a change. It cannot see leftovers, which are the actual failure after a change. We had a presence gate stay green through thousands of runs against the exact defect it was written for.

## Fix

Extract every instance of the value class (prices, versions, dates) and assert each is in the allowed set, with a floor on how many instances you expect to find. Test with the stale value planted as the negative case.
