title: A grep for pretty-printed JSON finds nothing in compact JSON
claim: 'A needle written as `"key": "value"` (with a space) matches `json.dumps` default output but not `JSON.stringify` or `jq -c` output, so a filter over compact logs reads 0.'
scope: any text search over JSON produced by different serialisers

check: |
  printf '%s\n' '{"status":"open","id":1}' '{"status":"open","id":2}' '{"status":"closed","id":3}' > rows.jsonl
  echo "defect: open=$(grep -c '"status": "open"' rows.jsonl)"
  echo "control: open=$(jq -c 'select(.status=="open")' rows.jsonl | wc -l | tr -d ' ')"
expected_defect: open=0
expected_control: open=2

---

## What goes wrong

Python's `json.dumps` writes `{"status": "open"}`. JavaScript's `JSON.stringify`, `jq -c` and most loggers write `{"status":"open"}`. A grep written by looking at one tool's output reads 0 against the other's.

## Why an agent hits it

Agents grep JSON logs because it is faster than writing a parser, and they type the needle the way they remember JSON looking. We once compared "before" and "after" counts that were both computed with a spaced needle over compact rows, and both were wrong the same way.

## Fix

Query JSON with a JSON tool (`jq`, a parser), not a string. If you must grep, allow optional whitespace (`'"status": *"open"'`) and check the needle against one row you know matches.
